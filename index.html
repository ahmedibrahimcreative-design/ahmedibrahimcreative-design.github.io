Case 01 Qiddiya Performing Arts Centre · Nesma & Partners · 2026

Twelve thousand documents nobody could get an answer out of.

  • Running now
  • Python pipeline
  • SHA-256 revision control
  • Used daily by the team

The situation. The project runs on Aconex, and Aconex will tell you a document exists. It will not tell you which of the four copies in your downloads folder is the current revision, which drawing covers the structure you are standing next to, or what changed between revision 01 and revision 02. So engineers hunted through folders, and when that failed they asked each other — which is how one person's memory quietly becomes the project's document control system.

What I built — a mirror that understands the numbering. A Python pipeline that reads the project register and files every document by parsing venue, document type and discipline straight out of the Aconex document number, into files/{venue}/{type}_{discipline}/. Every file is hashed with SHA-256, so a genuine revision change is never confused with a re-download and a prior revision is kept beside the new one instead of being overwritten. Every action appends to a permanent log. It also pulls Mail attachments — because recent attachments frequently never reach the Document Register at all, and the people who need them do not know that.

1,741files in the index the team actually opens

Then the working set was cleaned. The team's own folder tree had become a mess of near-duplicates. A consolidation pass took 941 raw files down to 564 canonical records: 361 exact duplicates identified by content hash and removed, reclaiming 2.5 GB; 374 controlled document numbers resolved; 16 revision-label aliases collapsed onto one record; 189 misfiled documents reclassified; and 376 PDFs opened, validated and their first page of text extracted so the set can be searched by content, not only by filename.

The deliverable colleagues touch is none of that. It is one page that opens in any browser — no install, no server, no internet — and finds any file by any fragment of a name, a document number or a structure ID, faceted by folder and by document type with live counts.

A file that could not be read is reported as unreadable, never as "not found". A scan result is unknown, not empty.

Design note — the distinction matters when someone acts on the output

The measurable outcome is retrieval time. The one that matters more is that finding a document stopped being a favour asked of whoever had been on the project longest.

Case 02 Temporary works control system · Nesma & Partners · 2026

A critical-risk discipline with no control system, governed in four weeks.

  • Live on project
  • Governance design
  • Consultant review addressed

The situation. Temporary works — the towers, formwork, scaffolds and foundations that hold a permanent structure up while it is being built — is the discipline where failures kill people. It had no documented control system on the project: no register of what existed, no rule for who was allowed to design what, no permit before a structure was loaded, and no way to answer the question a client auditor asks first — show me the evidence for this item.

What I did. I hold the formal appointment as Temporary Works Manager for the project and lead the team under it — a coordinator, three supervisors and three inspectors, allocated by work package. I treated the problem as a systems problem rather than a paperwork problem. One register that every temporary structure must appear on before it is designed, procured or built; the controls hanging off it — design categories, appointed roles, an inspection regime, permits that cannot be issued until the evidence behind them exists; and the detail that makes it survive contact with a real project: every status field links to the file that proves it.

An auditor should be able to verify any claim on the register in one click, instead of raising a document request and waiting three days.

The design rule the whole system was built around

Delivered iteratively, and the record shows it. The register went to site at Revision 00 and each revision after it added the layer that use had proved was missing — six revisions in nineteen days, every one triggered by something a real user could not do with the previous one.

Putting a specialist judgement in non-specialist hands. Deciding which design-check category a structure falls into governs how much independent checking it needs — and getting it wrong is either dangerous or expensive. It was a judgement only two people on the project could make. So I built it as a tool: describe the structure in plain language, tick what applies, and it returns the category, the inspection regime and the governing clause, alongside every categorisation the project has already decided. It proposes; the coordinator still decides.

The result that mattered. The client's consultant reviewed the plan and returned sixteen items — scope boundaries, duplication with quality procedures, document hierarchy, the treatment of variable inspection frequencies. All sixteen were addressed in a single revision, issued with a response matrix stating, item by item, what changed and the clause where it can be verified. On the most substantial of them — that a live inspection frequency should not be frozen inside an approved document — I had independently reached the same conclusion and already built the mechanism.

Case 03 Astron Arabia · lifting equipment inspection services · 2025 – 2026

Digitalising an inspection business from the inside.

  • Delivered
  • React 19 · tRPC · Drizzle · MySQL
  • 5 roles, 4 dashboards
  • ISO/IEC 17020 readiness

The situation. A third-party inspection company running its operations on spreadsheets, email threads and paper: timesheets collected by hand and recalculated by someone else, approvals living in an inbox, and technical records that had to be reassembled from several places whenever an accreditation audit asked for them. As Technical Manager I owned both the compliance outcome and the operational mess producing it — which is the position from which you find out what a process actually costs.

What I built. A full internal management application, not a form on a screen: React 19 and Vite on the front, Express and tRPC on the back, Drizzle ORM over MySQL, JWT authentication with refresh and revocation, rate-limited auth endpoints, token-based password reset, S3 for attachments, and PDF and Excel generation for the official outputs. Around 24,000 lines of TypeScript across seven database tables and sixteen screens.

  • Five roles, four dashboards — Admin, Manager, Reviewer, Employee and Developer, with branch-based data filtering so a manager sees their branch and a reviewer sees theirs plus the branches they are authorised to review.
  • End-to-end timesheet workflow — submission, automated calculation, review, administration, controlled approval with captured signature, and official PDF and Excel outputs. Draft, submitted, approved and rejected are real states, not a column someone types into.
  • Control produced as a by-product of normal use — validation, approval routing and duplicate prevention built into the workflow itself, with an audit log recording every approval, rejection, deletion and authentication event. Traceability happens because people did their job, not because someone remembered to police it.
  • Audit-grade data automation — Python and Excel automation filtering, matching and structuring thousands of records under time-critical audit conditions, turning unusable data into verified, traceable output.
  • Accreditation support systems — the technical records, impartiality controls and management review structure behind ISO/IEC 17020 readiness for an inspection body.

The transferable part is not the timesheet. It is that the compliance requirement and the daily workflow were designed as one thing. Systems that treat audit evidence as a separate exercise get abandoned the week the project gets busy.

In build Design Production System · personal build track, running now

An instrument, not a designer.

  • In development
  • Engineering documentation generation
  • Human-controlled by design

The most repetitive part of temporary works engineering is not the thinking — it is producing the package around the thinking: the analysis input files, the general arrangement drawing, the design brief, the calculation report, the check certificate, the schedules, the risk register. I am building a system that assembles all of that from a structured brief, so the engineer spends their time on the engineering.

It writes the analysis model for STAAD and SAP2000, an IFC model, layered and dimensioned DXF general arrangements, and the full document set. It never runs the analysis. The engineer runs it, on their own machine, under their own name.

Geometry comes from parameters a named person entered. Sections, steel grades, load magnitudes and the design category are never generated. Leave one blank and it becomes an open item printed into every output — including inside the analysis files — and the system withholds Perform analysis until it is closed. That refusal is the feature.

From the system's own design rules

The reason to state it that plainly: automation in a safety-critical discipline is only acceptable if the point where a human takes responsibility is structural rather than advisory. Reactions, member utilisation, buckling, base plates and connections are absent from the generated calculation report on purpose — they come from an analysis nobody has run yet, so the report carries them as headed, empty, labelled sections. And the governing rule for the whole build, written into its own progress ledger, is that the system never signs anything; every automated step ends at a named human.

Alongside it sits an independent verification track that reads the fabricator's issued model directly — parsing the IFC to extract the structure's connection graph, 15,812 connections between members, so a design can be checked against what was actually modelled rather than against what the drawing says was intended.
